# Decision 0004: Owner Intelligence Cockpit

- **Status:** Product direction accepted. Execution readiness: changes
  required before Phase 0 — see "Independent review" and "Revision history"
  below. This revision is not itself a claim that Codex has re-reviewed it.
- **Date:** 2026-08-07 (revised 2026-08-07, twice, after independent review
  and further scope decisions from Mohamed)
- **Owner:** Mohamed
- **Product:** El Kheima Beach Resort OS

## Context

Mohamed wants a dedicated application for the resort **owner** — not a second
super admin, not an operational role, not a page bolted onto the staff app.
The owner needs to see the true state of the business (accounting-accurate
revenue, profit, expense, and purchasing detail) using **real numbers only**,
understand why it is what it is, see risk and opportunity before they become
a crisis, and know immediately if theft or a clear financial problem is
happening — without being able to create, edit, approve, or cancel anything.
The experience must be mobile-first (the owner mainly opens it on a phone),
pull-based (he opens the app and finds what he needs; the product does not
push reports over WhatsApp), and must feel like a distinct, professional
analytical product rather than a reskinned page from `el-kheima`.

This record follows the same discipline as
`docs/decisions/0003-super-admin-control-plane.md`: it defines the accepted
direction and its non-negotiable invariants. It is not a claim that any of it
is built yet.

### Independent review

Codex reviewed the first version of this record on 2026-08-07 and found ten
execution-readiness gaps before Phase 0 could safely start: a direct conflict
with Decision 0003's super-admin invariant, a read-only database session that
could not perform the writes the plan itself required, an ownership model
that let the owner influence the profitability numbers he views, a phase
order with an internal contradiction and an unsafe AI-before-numbers
sequence, an inaccurate frontend fact, missing metric definitions, test
coverage that could not see WebSockets or future routes, an incomplete
account lifecycle, an unimplementable versioning description, and two
smaller consistency issues. Two of the underlying factual claims were
verified directly against the code before accepting that revision:
`get_timeshare_admin_user` in `backend/app/core/deps.py` explicitly returns
early for `user_level(user) >= 100`, commented `# super_admin — Decision
0003 invariant #1`, before it checks the role name; and no `playwright`
reference or `playwright.config.*` exists anywhere in this repository today.
All ten points were accepted and folded in.

### Revision history

After the review above was incorporated, Mohamed made three further scope
decisions, also folded into this version:

1. **No external AI, no chat, in any form.** The originally planned
   "Narrative intelligence" and "Ask your business" features (both required
   a Gemini/LLM call) are **removed from scope entirely** — not deferred,
   removed. The product is 100% real, computed numbers; nothing is
   generated by a language model, and no business data is ever sent to a
   third-party AI service.
2. **Beach entry, ticket types, and hotel B2B partner contracts** are
   explicitly in scope for sales/channel analytics, using data that already
   exists in the `beach` module.
3. **Staff-on-shift visibility and theft/financial-irregularity detection**
   are explicitly in scope, built on the finance module's existing shift and
   cash-movement data plus the existing fraud-signal detection — not a new
   capability invented for this record.

## What this is deliberately not

- **Not a second super admin and not a control plane.** The owner role has no
  authority over users, roles, permissions, settings, or any operational
  workflow. Decision 0003's invariants are untouched by this record —
  including invariant #1, which this revision honors explicitly (see
  "Isolation model" item 2).
- **Not a new business domain**, unlike `timeshare`. `timeshare_admin` is
  isolated because it owns a genuinely separate slice of data. The owner role
  owns almost no data of its own — it is a read-only aggregation layer over
  every existing module, plus a thin, explicit configuration surface (see
  "Unit economics governance" — the owner drafts and experiments; he does not
  unilaterally publish the rule his own numbers are judged by). It must not
  accumulate a parallel set of business tables.
- **Primary metrics are not recomputed.** Every primary figure shown to the
  owner (revenue, cash, expense, occupancy, receivables) is produced by
  calling the same finance/dining/beach/inventory/pms/timeshare service
  functions every other part of the application already calls for that
  number. Derived metrics (ABC classification, per-item margin, variance,
  unit economics) are new computations over those primary numbers — see
  "Numbers must equal the source of truth" for the precise distinction. If a
  primary figure and its accountant-facing equivalent can ever diverge, that
  is a defect in this feature, not an acceptable rounding difference.
- **Not delivered by push.** No WhatsApp report delivery, no proactive
  messages for routine content. The owner opens the product and finds
  everything current. The one legitimate exception is a security notification
  for a new-device login on the owner's own account — that protects his
  account, it is not a business report.
- **Not powered by any AI, internal or external.** No chat, no free-form
  question box, no auto-generated narrative text, no call to Gemini or any
  other language model, anywhere in this feature. Every screen shows
  computed numbers, tables, and rule-based flags (e.g. "up 12% vs last
  Thursday," a fixed comparison computed in plain code) — never generated
  prose. This is an explicit, final decision, not a deferred one.
- **Not built on a new heavy dependency.** The project has no `pandas` or
  `numpy` today and does not need them at single-resort data volumes. Every
  computation this record calls for (ABC/Pareto classification, item margin,
  trend/variance detection) is achievable with the standard library
  (`decimal`, `statistics`) combined with the project's existing SQL
  aggregation idiom, consistent with `resort_os/food_cost_engine.py` and
  `resort_os/discount_engine.py`.
- **Not individual guest surveillance.** Where guest spending is shown for a
  B2B hotel-partner channel (see scope item 6), it is aggregated **per
  hotel/contract**, never per named guest. No guest name, phone, or personal
  identifier is ever surfaced on any owner screen.

## Scope

1. **Now** — a single mobile screen built only from metrics that have a
   written contract (see "Metric contracts" below).
2. **Performance** — day/week/month/year comparisons and prior-period /
   prior-year comparisons, computed by calling the existing report functions
   twice (or across a range) and diffing, not by a separate comparison
   engine.
3. **Sales / product & service performance** — which products and services
   actually sell and actually make money: ranked lists, ABC/Pareto
   classification, real per-item margin where recipe costing exists, trend
   direction per item. Extends to **beach operations**: check-ins/entries by
   ticket type, capacity utilization, and revenue per ticket type, sourced
   from the existing `BeachLocation`/`BeachTransaction` data (the same data
   the live beach map already uses).
4. **Expense analytics** — every expense category as a percentage of
   revenue over time (not absolute figures alone), with automatic variance
   flags when a category's share of revenue moves abnormally.
5. **Procurement / purchasing analytics** — spend concentration by supplier,
   price trend per purchased product over time, purchase-request-estimate
   vs. purchase-order-actual variance.
6. **Channel / B2B partner analytics** — performance of each hotel B2B beach
   contract (`B2BContract`): volume, revenue, credit-limit and overdue
   status (this already exists — `credit_limit`/`is_overdue` on the model),
   and each partner's guests' aggregate F&B attach — how much a hotel's
   referred guests spend on dining/cafe on average, and their top items —
   reported **per hotel/contract only**, never per named guest.
7. **Staff on shift and cash-control monitoring** — who is currently working
   (open cashier shifts, from the existing `finance/shifts/active`), and for
   each shift: the cash variance at close, and any manual cash movement
   (drop, correction, petty cash) recorded during it. This surfaces the
   finance module's existing shift/cash-control data to the owner; it does
   not add new shift-management capability, and the owner cannot act on any
   of it (no approve/close/dispute from this surface).
8. **Exceptions** — an always-current, severity-ranked list of things that
   deserve the owner's attention: fraud/anomaly signals (generalized from
   the existing detection in `app/tasks/fraud_tasks.py` — refund/void/
   discount/drawer-open thresholds per cashier), abnormal shift cash
   variance from item 7, and the expense/procurement variance flags from
   items 4–5. This is the concrete answer to "will I know if theft or a
   clear financial problem happens" — it is not a separate promise, it is
   this list.
9. **Unit economics** — profit per room-night, beach unit, table/dish, and
   timeshare unit, gated on the governance model in "Unit economics
   governance" below. Never invented by the system.
10. **Scenario sandbox** — transparent, assumption-based projections
    ("if X changes and Y stays fixed, the range is A–B"), explicitly not a
    trained forecasting model.

Items 1–8 are the core of the product and are built and shown to Mohamed
before items 9–10 exist at all (see "Controlled implementation sequence").
This is a Priority #3 (new feature) initiative under `CLAUDE.md` §2 and must
not be allowed to crowd out Priority #1/#2 work without Mohamed's explicit
say-so for this initiative.

## Isolation model (non-negotiable invariants)

1. **Role.** A new `owner` role is added to `ROLE_LEVELS` in
   `backend/app/core/deps.py` **and** the matching table in
   `frontend/packages/core/src/stores/auth.ts` (the shared `ROLE_LEVELS`
   consumed by every frontend app, not a per-app copy), per the existing rule
   that the two must stay identical (`CLAUDE.md` §13 item 5). Its numeric
   level is placed low — **below `employee` (20)** — specifically so it can
   never accidentally satisfy an existing `>= N` level check anywhere else in
   the application.
2. **Dependency — `get_owner_reader`.** Named deliberately differently from
   an earlier draft's `get_owner_user` to make its shape clear: it accepts
   `role == "owner"` **or** `user_level(user) >= 100` (`super_admin`),
   exactly the pattern already implemented in `get_timeshare_admin_user`
   (verified: it checks `super_admin` first, citing Decision 0003 invariant
   #1 by name in its own comment) and required by Decision 0003 invariant #1
   itself ("An active `super_admin` passes all application permission
   checks"). This does **not** give the owner any super-admin capability —
   it only means a super admin is not locked out of a surface that is
   read-only for everyone, including him. If a future decision is to exclude
   `super_admin` from this surface specifically, that requires an explicit
   amendment to Decision 0003, not an implicit exception buried in this
   module. The frontend mirrors this: `ROLE_LEVELS`/`hasRole()` in
   `stores/auth.ts` is for generic display/guard use only — real access to
   the owner app's routes is gated by a direct role-name check
   (`owner` or `super_admin`) in the new `frontend/apps/owner`'s own
   `router/index.ts` (`requiredRoles`), the same two-layer pattern already
   used for `timeshare_admin`.
3. **Mandatory 2FA.** Add `"owner"` to `MANDATORY_2FA_ROLES` in `deps.py`.
4. **Central write block — structural, not a bolt-on sweep.** Level
   isolation alone is **not sufficient**: a code audit for this record found
   real mutating endpoints (for example `POST /crm/customers`,
   `PATCH /crm/customers/{id}`, `POST /beach/transactions/{id}/void`, and
   others across `crm`, `beach`, `hub`, `inventory`) authorized only by
   `get_current_active_user`, i.e. any active session regardless of role
   level. The fix must live **inside the authentication dependency chain
   itself** as an owner request-policy layer, not as a separately
   maintained list checked by a sweep test after the fact:
   - A registry of the owner's allowed actions keyed by **route name**
     (FastAPI's `route.name`/`operation_id`), not URL string matching, which
     is fragile against path-parameter and prefix variance.
   - The registry allows exactly: the owner's own profile, 2FA/session
     management, `OwnerWatchlist` writes, and the owner's allocation-rule
     **draft** endpoints (never the publish/activate endpoint — see "Unit
     economics governance").
   - **Fail closed by default.** Any route not present in the registry —
     including one added after this record is written — is denied to
     `owner` automatically. The registry is an allowlist, never a denylist.
   - Operational **WebSocket** endpoints (the KDS ticket stream, the beach
     live map at `/beach/ws/map/{branch_id}`) do not appear in the OpenAPI
     schema and must be explicitly rejected for `owner` in the same policy
     layer, not assumed covered by the REST test below.
   - `branch_id` and any other trust-sensitive context for an owner request
     is derived server-side from the authenticated session, never accepted
     from the client, consistent with the project's existing branch-trust
     rules.
5. **Database session model.** The owner surface needs to read broadly and
   also legitimately write in three narrow places (its own audit trail, its
   own preference/draft tables). A single "read-only session" cannot do
   both, so the implementation uses three sessions:
   - **`OwnerReadSession`** — bound to a dedicated PostgreSQL role granted
     `SELECT` only on business schemas. Used for every aggregation/report
     read.
   - **`OwnerMetadataWriteSession`** — a narrowly granted role limited to
     `INSERT`/`UPDATE`/`DELETE` on `owner`-module tables only
     (`OwnerWatchlist`, allocation-rule drafts) — no access to any business
     table.
   - **Audit writer** — reuses whichever mechanism already writes
     `AuditLog` elsewhere in the codebase (do not invent a second one); if
     that mechanism needs a dedicated grant, it is `INSERT`-only on
     `audit_logs`.
   A required acceptance test runs against real PostgreSQL (not SQLite,
   which silently ignores privilege and locking behavior the project has
   already been burned by — see `CLAUDE.md` §13 item 11) and proves that an
   `INSERT`/`UPDATE`/`DELETE` attempted through `OwnerReadSession` fails at
   the database level, not merely at the application layer.
6. **Audit — signal, not noise.** `audit_logs` receives an entry for a
   deliberate report open, a sensitive drill-down, an export, and any
   settings/allocation-rule action — **not** for routine auto-refresh/
   polling on a live screen, which would flood the table with zero-value
   rows and work against the audit trail's own purpose. No second audit
   table — the project has an explicit, documented decision against that
   (see `fraud_tasks.py`'s module docstring).
7. **No new PII exposure.** Payroll appears as an aggregate and a percentage
   of revenue by default, never itemized per employee. An employee's name
   appears only when directly tied to a flagged exception (for example a
   cashier fraud signal or an open shift they are working) — never as
   general roster access. Guest personal data is never surfaced; B2B channel
   analytics are aggregated per hotel/contract only (see scope item 6).
8. **No AI, no external service call, anywhere in this module.** Reinforced
   here as an isolation invariant, not just a scope note: the owner backend
   never calls an LLM, never sends business data to a third party, and has
   no chat/free-text endpoint of any kind.

## Metric contracts (must exist before Phase 3 writes any service)

Terms like "net cash position," "today's expense," "forecast occupancy," and
"overdue receivables" are not yet precisely defined anywhere in the codebase,
and some may not exist today as a single unified report. Before any owner
service is implemented, every metric the product will show gets an entry in
a KPI dictionary specifying:

- The exact formula.
- Its source of truth (which existing function/table it comes from).
- The period and timing it applies to.
- Inclusion/exclusion rules.
- Whether it is a book balance or a reconciled balance.
- For occupancy: confirmed bookings on the books, or a statistical forecast
  — these are not the same thing and must not be silently conflated.
- For receivables: whether "overdue" spans folios, timeshare installments,
  B2B contracts, and leasing together or is reported separately per source.
- Its data-completeness status: provisional / posted / closed.
- The drill-down path that proves the number (what the owner sees when he
  taps it).

A metric with no contract entry does not get a service function, an
endpoint, or a place on the "Now" screen. Phase "Metric contracts and
data-readiness audit" (see below) exists specifically to write this
dictionary and confirm, for each entry, whether the underlying unified
report already exists or still needs to be built.

## Numbers must equal the source of truth

**Primary metrics** — revenue, cash, expense by account, occupancy,
receivables, beach ticket counts/revenue, B2B contract balances, open-shift
status — are read directly from the existing sources of truth:
`finance/reports/income-statement`, `.../balance-sheet`,
`.../trial-balance`, `finance/cost-centers/report`, `finance/periods`,
`finance/journal-entries`, `finance/shifts/active`, and the equivalent
dining/beach/pms/inventory service functions. Nothing here is recomputed.

**Derived metrics** — ABC/Pareto classification, per-item margin,
trend/variance flags, unit economics — are new computations performed in
`app/resort_os/owner_analytics_engine.py`, over the primary metrics above,
with a full and inspectable lineage back to the primary inputs each one was
derived from. A derived metric is not "the same report called directly";
its acceptance test is that its output is correctly derived under `Decimal`
arithmetic from stated primary inputs and defined data semantics — not a
literal byte-for-byte comparison, which does not meaningfully apply to a
newly computed value.

Every number, primary or derived, carries: the period it covers, whether
that period is closed (posted) or still open/provisional (from
`finance/periods`), and a computed-at timestamp. The owner cockpit must
never present a provisional number as if it were final.

## New engineering surface

- **`app/modules/owner/`** — a normal module following the project's
  five-layer convention (`models.py`, `schemas.py`, `crud.py`, `services.py`,
  `api/router.py`). Its own tables are limited to `OwnerAllocationRule`
  (versioned — see "Unit economics governance") and `OwnerWatchlist`
  (pinned metrics/preferences). No other domain tables. No AI/chat tables.
- **`app/resort_os/owner_analytics_engine.py`** — a pure engine (no FastAPI
  or SQLAlchemy imports, matching `food_cost_engine.py`/`discount_engine.py`)
  containing: ABC/Pareto classification, per-item margin computation given
  recipe-cost and sale-price inputs, trend/variance detection using
  `statistics` from the standard library, and the shift-variance/exception
  scoring used by scope items 7–8. All deterministic; no AI call anywhere in
  this file or anything it calls.
- **`OWNER_EXCEPTION_RULES`** — a single catalog dict inside the owner
  module, following the exact pattern already established by
  `app/modules/core/policy_engine.py`'s `SENSITIVE_ACTIONS` and
  `permission_catalog.py`. Ranking is **tiered first** (`critical` /
  `attention` / `watch`, with operational safety and suspected-theft signals
  hard-pinned to `critical` regardless of financial size), then sorted by
  `impact × confidence` inside each tier. Every exception is tagged
  `realized` / `projected` / `potential`. Reuse `fraud_tasks.py`'s existing
  signals and the shift-variance data from scope item 7 as exception
  sources instead of duplicating detection logic.
- **Sales performance service** — generalizes the existing `top_items`
  query in `app/modules/dining/api/router.py` (currently inline in one
  endpoint, dining-only, ranked by quantity only, and using `float()` for
  money) into a reusable, multi-outlet service that ranks by revenue and
  margin as well as quantity, uses `Decimal` throughout, and is extended to
  cover beach ticket types using the same shape.
- **Channel analytics service** — reads `B2BContract` and its associated
  beach transactions/dining orders (via existing `customer_id`/contract
  linkage) to produce per-hotel volume, revenue, credit/overdue status, and
  aggregate F&B attach — grouped by contract, never by individual guest.
- **Shift monitoring service** — reads `finance/shifts/active`,
  `CashierShift`, and `CashMovement` to produce the "who's on shift now" and
  "cash variance" views in scope item 7, and feeds abnormal variance into
  the exceptions catalog above.
- **Frontend — `frontend/apps/owner`.** This is the **second** active
  internal application in this monorepo, after `frontend/apps/el-kheima` —
  not a third alongside `public`. Per `AGENTS.md`, the marketing/guest site
  now lives in the independent `elkheima-marketing-website` repository and
  is not part of this workspace. Mobile-first PWA, dark-first, card-based,
  sparkline-driven design system distinct from the staff BackOffice, reusing
  only `@resort-os/core` (API client, auth store) and genuinely generic
  parts of `@resort-os/ui` (currency/date formatting, i18n/RTL, accessibility
  primitives). The router refuses to render for any non-`owner`/
  non-`super_admin` session client-side, mirroring "Isolation model" item 2.
  Before the frontend phase starts, these must be decided explicitly (by
  Mohamed/Codex, not assumed): the app's domain
  (`owner.elkheima.com` vs. a path under the existing staff domain), its
  CORS and reverse-proxy configuration, its cookie/token scope, and its own
  deploy/rollback policy. Because this is a mobile PWA carrying financial
  data: no API/business data may be cached in a service worker or
  IndexedDB — only static assets are cacheable; every financial API
  response is served `Cache-Control: no-store`; and all cached/stored
  client state is cleared on logout and on session revoke.

## Unit economics governance

Per-unit profitability (room-night, beach unit, table/dish, timeshare unit)
depends on cost-allocation rules (utilities, shared payroll, depreciation,
shared beach cost, channel commission) that materially change which part of
the business looks profitable. Letting the owner unilaterally set the rule
his own profitability is judged by is a conflict of interest the "owner is
view-only" principle exists to prevent. The governance is therefore:

- The owner may create **drafts** and run what-if experiments freely inside
  the Scenario Sandbox. Drafts never affect any number shown outside the
  sandbox.
- Only `super_admin` or `accountant` can **activate** the rule version that
  actually feeds reports, after Mohamed's approval, requiring step-up
  authentication, a mandatory written reason, an `AuditLog` entry, and
  producing an immutable published version.
- `OwnerWatchlist` entries and personal filters/preferences remain the only
  writes the owner can make unilaterally.
- Each published version carries `effective_from` (and optionally
  `effective_to`). A published version is never edited in place — a change
  creates a new version, mirroring `AGENTS.md`'s existing rule that posted
  financial records are corrected through reversal/replacement, not
  in-place edits.
- A historical/period report selects whichever rule version was effective
  for the **accounting period being reported**, not whichever version is
  active when the report happens to be viewed.
- When an accounting period closes, the rule version used for that period's
  unit-economics figures is recorded against the period, so a later rule
  change can never silently rewrite a closed period's numbers.
- Open decision to resolve before the unit-economics phase: what unit
  economics (if anything) is shown for periods before the first published
  rule version. Default to "not shown" unless Mohamed decides otherwise.

project's existing Definition of Done (`CLAUDE.md` §3.8 / `AGENTS.md` §8)
before the next phase begins. Whether and when a completed phase is
**committed** is a separate decision from whether it is *done* — see "Work
instructions" below. No phase includes a production deployment.

### PerformanceScreen breakdown (accepted addition, 2026-08-08)

The current `/api/v1/owner/performance` returns revenue/expense/net income
totals only. After Phase 6 is complete (when outlet-level analytics exist),
`OwnerPerformanceResponse` is extended with an optional `breakdown` field:

```
breakdown: {
  dining_revenue:  Decimal | None
  beach_revenue:   Decimal | None
  rooms_revenue:   Decimal | None
  other_revenue:   Decimal | None
}
```

Rules:
- `None` for any outlet means its data is not yet available for the period
  (provisional or no transactions), never zero-filled silently.
- The frontend `PeriodComparisonCard` adds a collapsible breakdown row
  below the main totals — collapsed by default, one tap to expand.
- No new table or new aggregation function: `dining` revenue comes from
  `get_income_statement`, beach from `BeachTransaction` sum, rooms from
  PMS folio totals — the same sources Phase 6 will already have wired.
- Acceptance: each breakdown figure equals its Phase 6 outlet-level service
  output for the same period (`Decimal` equality in tests).
